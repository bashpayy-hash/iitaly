# IITALY: WhatsApp Cloud API — подготовка интеграции

## Статус и границы

Это проверяемый код-каркас, **не включённая рассылка**. `server.js`, Railway,
существующие кабинеты, цены, чат, Telegram и планировщик не меняются.
Нет новых npm-зависимостей. `WHATSAPP_MODE=off` по умолчанию. Meta-аккаунт,
номер, секреты и шаблоны этим PR не создаются и не регистрируются.

Файлы:
- `client.js`: отправка только шаблонов; off/test/production; в тестовом режиме
  строгий список 1–5 получателей; проверка серверного согласия и номера;
  таймаут; различие accepted/rejected/unknown, без слепых повторов.
- `webhook.js`: GET-подтверждение Meta, обязательный HMAC-SHA256 исходных байтов,
  фильтр WABA/Phone Number ID, нормализация статусов, LINK и STOP,
  стабильные ключи для дедупликации; ответ 200 только после успешного сохранения.
- `linking.js`: случайная одноразовая ссылка на 10 минут; в хранилище — только
  хеш токена. Номер берётся из подписанного события Meta, не из формы браузера.
- `templates.ru.json`: три **черновика**, не одобренные Meta шаблоны. Один due
  используется для 7/3/1 дня, плюс overdue и weekly digest. Категория UTILITY
  запрашивается для уведомлений по сохранённому маршруту, но не гарантируется.

## Порядок подключения

### 1. Защитить данные до любого деплоя

При предыдущем read-only аудите production Railway не имел постоянного тома.
Сначала сохранить данные работающего контейнера в закрытое хранилище и проверить
восстановление, затем безопасно мигрировать в постоянное хранилище и настроить
резервные копии. **Не менять DATA_KEY; не подключать пустой том с перезапуском
до спасения текущих данных.** Этот PR не выполняет миграцию и не снимает блокер.

### 2. Настройка Meta со стороны владельца IITALY

Создать/выбрать Business Portfolio и WhatsApp Business Account, приложение Meta
с WhatsApp и бизнес-номер. Подтвердить владение номером, настроить отображаемое
имя, биллинг и пройти проверки, которые запрашивает Meta. Для существующего
номера сначала проверить поддерживаемую схему переноса/совместного использования;
не удалять рабочую WhatsApp-учётную запись ради эксперимента.

В приватном серверном окружении задать переменные из `.env.example` рядом с этим
файлом. Токен — серверный System User token с нужными правами на выбранный WABA
и номер. Для отправки требуется `whatsapp_business_messaging`, для управления
шаблонами — соответствующий `whatsapp_business_management`. Не использовать
временный токен панели как постоянную настройку. API version выбрать актуальную
в Meta явно: код не фиксирует устаревающую версию. Пример v25.0 в тестах — лишь
синтетическая проверка формата, не рекомендация версии.

Нельзя помещать токены в Next.js, NEXT_PUBLIC_*, публичный репозиторий, логи или
переписку. App Secret для HMAC и Webhook Verify Token — разные значения.

### 3. Шаблоны и согласие

Загрузить черновики из `templates.ru.json` в WhatsApp Manager, проверить тексты,
статическую кнопку `/portal`, примеры и русский язык, дождаться одобрения.
Не нужен отдельный шаблон на каждый из 7/3/1 дней: это параметры одного due.
Никаких рекламных вставок или обещаний поступления/стипендии. Сводка должна
соответствовать тому, на что пользователь согласился. Meta может изменить
категорию, отклонить или приостановить шаблон.

Текст согласия для будущей формы (чекбокс изначально выключен):
«Хочу получать от IITALY напоминания о дедлайнах моего плана и еженедельную
сводку в WhatsApp. Их можно отключить в кабинете или ответом СТОП».
Форма и обработка согласия в действующем кабинете **пока не подключены**.

### 4. Подключить к постоянному хранилищу и существующей авторизации

Предлагаемые новые маршруты, ещё НЕ зарегистрированные в server.js:
- POST `/api/portal/:code/whatsapp/link`: существующая авторизация кабинета,
  ограничение частоты и явное согласие. `issueLink` получает внутренний accountId
  только от проверенного сеанса, не из произвольного поля запроса.
- POST `/api/portal/:code/whatsapp/disable`: атомарно выключить подписку,
  погасить незавершённые токены и отменить ещё не отправленные задания.
- GET/POST `/api/whatsapp/webhook`: подтверждение и подписанные события Meta.

`store.insertLink(record)` должен атомарно инвалидировать предыдущие ссылки
пользователя и сохранить новую запись до выдачи URL. Ограничить число активных
ссылок, хранить TTL. Нельзя подменять реализацию объектом в памяти в production.

`persistEvents(events)` — транзакция с дедупликацией по event.key:
1. LINK: проверить токен/expiry/пользователя, вызвать subscriptionFromLink,
   атомарно погасить токен и сохранить подписку. Привязка — только к отправителю
   подписанного события. Повтор LINK не должен снова включить подписку после STOP.
2. STOP: выключить подписки этого подтверждённого номера, записать отписку,
   погасить токены и отменить очередь. Работает и при выключенной отправке.
3. STATUS: найти исходящее сообщение по messageId И номеру, затем advanceStatus;
   не создавать доставку для неизвестного сообщения. Не понижать read/delivered
   из-за опоздавшего sent/failed. Записать event.key и изменение одним коммитом.
Вернуть true только после долговременной записи. Сбой — исключение/false → 503.
Если используется inbox+worker, сначала нужна устойчивая очередь, приоритет STOP
и гарантии, что новые отправки не обгонят уже принятую отписку.

### 5. Подключить webhook ДО глобального JSON parser

Ниже пример сборки, НЕ код, уже исполняющийся на production:

```js
const { createWebhookHandlers } = require('./integrations/whatsapp/webhook');
const handlers = createWebhookHandlers({
  appSecret: process.env.WHATSAPP_APP_SECRET,
  verifyToken: process.env.WHATSAPP_WEBHOOK_VERIFY_TOKEN,
  wabaId: process.env.WHATSAPP_BUSINESS_ACCOUNT_ID,
  phoneNumberId: process.env.WHATSAPP_PHONE_NUMBER_ID,
  persistEvents: events => whatsappStore.applyBatch(events), // durable transaction
});
app.get('/api/whatsapp/webhook', handlers.verify);
app.post('/api/whatsapp/webhook',
  express.raw({ type: 'application/json', limit: '256kb', inflate: false }),
  handlers.receive);
// Existing app.use(express.json(...)) follows these routes, not precedes them.
```

Meta: публичный HTTPS callback, совпадающий verify token, подписка на `messages`
для правильного WABA. Одного успешного GET challenge недостаточно: POST всегда
проверяется отдельной HMAC-подписью. Пример whatsappStore — требуемый адаптер
хранилища, не включённый в этот PR; его нельзя заменить заглушкой `return true`.

### 6. Очередь и связь с reminder PR #4

Не добавлять WhatsApp к старому условию `okOwner || okClient`. В PR #4 подготовлен
раздельный учёт Telegram/email; WhatsApp нужен отдельный outbox и история.
Ключ: accountId + задача + точный дедлайн + порог + канал + версия получателя.
Планировщик выбирает дату из сохранённого маршрута, не из сгенерированного текста.
Проверяет выполненность, отписку, quiet hours и часовой пояс; атомарно занимает
задание; непосредственно перед сетью перечитывает подписку; вызывает client.send.

`accepted` означает только принятие Meta и wamid, НЕ доставку. После него не
повторять из-за отсутствия read. `rejected` повторяется лишь для retryable=true,
с паузой и лимитом попыток. `unknown` (таймаут/потерянный ответ) требует сверки,
а не автоматического повторного POST: иначе возможны дубликаты. Подписанный
failed надо сопоставлять с попыткой и классифицировать по коду ошибки.

Сбой между приёмом Meta и локальным сохранением нельзя превратить в гарантию
exactly-once. Не называть принятие API доказательством push на телефоне.
Текущая очередь, хранение согласий и фронтенд-переключатель WhatsApp этим PR
**не реализованы**. Код специально не импортирован в server.js до их подключения.

### 7. Тест и запуск

После сохранения данных: отдельное staging-окружение; WHATSAPP_MODE=test;
1–2 согласованных номера в allowlist; одобренные шаблоны. Проверить реальную
привязку → шаблон → delivered/read → уведомление на телефоне → СТОП → отсутствие
следующих отправок. Не вызывать глобальный /api/reminders/run для одного теста.
Затем ограниченный запуск с бюджетом/лимитами и наблюдением за ошибками.

## Стоимость

Meta публикует тарифы по рынку получателя и категории и тарифицирует доставленные
сообщения. Есть бесплатные сервисные сообщения и определённые utility-ответы.
Не считать все дедлайн-уведомления бесплатными. Для оценки: количество платных
доставленных шаблонов × применимая ставка + хостинг/хранилище; посредник может
добавлять свою плату. Конкретная ставка для казахстанских получателей в этом PR
не зафиксирована: сверить актуальную rate card перед подключением биллинга.
